# 天津九年级化学题库

本地网页题库，按人教版九年级化学的单元和课题浏览、检索和组卷。在本机运行，无需登录。给家人用的。

简述一下这个东西是干嘛的，以及它目前是什么样子：主要是因为家人那边有需求，需要让 AI 改写部分题目拿给学生做。

现有的流程是：

1. 先把卷子差不多编好。
2. 把卷子丢给某一个 AI，让它找错别字或者做些基础处理。
3. 也有尝试过直接把整个文档丢给 AI，让它修改某些题目，让题面更灵活、对学生知识点的考察更全面。但效果不尽如人意，而且非常不灵活。

这里比较棘手的一点是它的格式是 Word。在编辑这方面，Word 作为富文本编辑器，确实比 Markdown 复杂不少。然后就是化学题目，它有一个特点，就是图片其实蛮多的，真的是蛮多的。这其实就给整件事情增加了难度。


## 如何运行

```bash
python3 -m venv venv
source venv/bin/activate
pip install python-docx lxml
python app.py serve
```

浏览器打开 http://127.0.0.1:8765 。

变式生成会从环境变量读取 `GLM_API_KEY` 和 `DEEPSEEK_API_KEY`。没有这两项时，浏览和组卷仍可使用。不要把密钥写进代码或提交到仓库。

## 不在本仓库中

题目数据库（`bank.sqlite`）和题目图片（`media/`）没有放进本仓库，需要在本机自行准备后再启动。

## 正式运行

```powershell
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe app.py serve
```

默认地址 http://127.0.0.1:8765 ，使用项目根目录的题库。`CHEM_DATA_DIR` 可指定独立数据目录，`CHEM_PORT` 指定端口，`CHEM_MIRROR_DIR` 指定批量导入源目录。正式启动会进行兼容的附加表迁移；先备份现有题库。现有题号和教师已保存的题型、分类、题干会保留。旧题不自动全库重判，页面显示新的识别建议供核对。

通过环境变量 `GLM_API_KEY` / `DEEPSEEK_API_KEY`，或本机已有的 `keys.local` 配置 AI。不要提交密钥。`CHEM_DISABLE_AI=1` 关闭工作线程与生成调用。保留母题分析、生成、独立审题和版本选择流程，课标约束和图中条件锁定贯穿分析、改写与审题。

## 识别与导出

- 优先采用原卷题型标题；装置 A/B/C/D 和综合题的局部选项不会仅凭字母把整道题判为选择题。
- 支持换行粘连题号、Word 自动编号、布局表格里的题目、单独答案区及“24（6分）”题号。边界或答案对应不明确时提醒核对。
- 保留文字上下标、原生 OMML 和图片。Windows 用系统绘图库生成 WMF/EMF 网页预览，Word 导出保留原始矢量字节；缺失图片或未读取嵌入对象会阻止不完整导出。
- 答题空在网页显示为连续横线，Word 导出保留单下划线格式。兼容旧题干中由空格隔开的下划线；新导入支持带下划线的不换行空格。
- 中文上传文件名以 UTF-8 保存。已有乱码文件名显示可读取的文档标题并提示名称异常，原路径保留，不推测无法恢复的中文原名。
- 新增国家课标五个主题及 30 个项目知识点建议，综合题可有多个标签。标签仅供检索，不是天津官方考试权重或教师已确认的考点。
- 单次导出最多 500 题，超出明确提示，不截掉题目。批量导入改为增量合并，保留组卷引用和教师修正。

原生 OMML 在 Word 中仍可编辑。旧公式编辑器对象若有图片表示则保留图片；没有可读取表示的对象需教师核对。嵌套表格、复杂浮动布局、多层编号和跨页答案对应仍可能需要人工处理。旧 `.doc` 需要 LibreOffice，没有该程序时请在 Word 另存为 `.docx`。本次没有安装系统级 Word 或 LibreOffice，没有完成实际打印分页验证。

## 已导入题库如何升级

程序升级不会自动重建或全量修改已有题库。横线显示、来源显示和导出行为使用新版后可生效；旧题型和知识点提供建议，保留教师已保存的修正。已经粘连或缺失图片、公式的旧题，需要从对应原 Word 重新解析后定向修复。

重复导入目前按去重键增量合并，不是覆盖修复模式。全量重新解析应在备份后的独立数据目录中进行，并另行核对已有试卷引用和教师手工修改的保留；不要直接清空正式题库。

## GLM 速度与带图请求补充（2026-10-02）

真实 API 排查复现了带图分析返回 HTTP 200 但正文为空的问题：GLM 默认最大推理强度，加上原来的 4096 输出 token 上限，导致预算被推理消耗，结束原因为 `length`。新版对 GLM-5.3 显式设置 `reasoning_effort=high`，输出额度默认 8192，保留分析、改写和独立审核三步。配置和实测记录见 [GLM 性能与图片问题排查](docs/GLM性能与图片问题排查.md)。

可通过 `GLM_REASONING_EFFORT=low|high|max` 调整推理强度，通过 `GLM_MAX_TOKENS` 调整输出额度（程序允许 512 至 32768）。输出额度包含推理开销；增大上限可能增加耗时与费用。GLM-5.3 不使用 `thinking.type=disabled`。图片缺失或格式不可用会明确报错，不静默退为纯文字；单题图片不再只取前 8 张，程序上限为 32 张，超过时提示核对题目粘连。

页面区分等待处理、分析原题、改写和独立审核；输出额度耗尽、接口错误、缺图等失败原因会显示。GLM 失败后仍保留 DeepSeek 备用调用，两者均失败时保留 GLM 原因。单次普通聊天的耗时不能等同于完整三步组卷变式流程，自动审核通过仍需教师最终确认。

## 等待时的页面说明

AI 处理时，题目下方会显示“正在等待开始”“正在读懂原题”“正在改写题目”或“正在检查题目和答案”，并解释当前在做什么。页面同时提醒带图题有时需要一分钟或更久、结果会自动更新，无需重复点击；批量处理会提示分批等待。失败时以普通用户能理解的语言说明没有写完、等待太久、服务繁忙或图片不可读取等情况，详细原因仍保留在本地记录中供排查。

## Grok Bot 本地检索与组卷

提供 `chem_bot.py` 专用命令工具，让 Grok Bot 在实际用户电脑上检索已收入题库的题目，并新建可直接查看的试卷。支持关键词、题型、图片、知识点和分页，校验题库版本、真实题号及图片完整性；同一任务重复提交只创建一套试卷，原题和已有试卷保留。用户不需要重新导入 Word，程序沿用题目中的图片和格式。

首次需维护者配置 Grok Bot 的本地执行能力、项目虚拟环境、正式题库目录及实际端口，之后用户可直接向指定 bot 提要求。安装好环境后可双击 `打开化学题库.cmd`。完整配置、命令、验收步骤、可复制的交接与长期工作 prompt 见 [Grok Bot 接入与交接](docs/Grokbot接入与交接.md)。Grok Bot 的云端电脑不能直接访问家人电脑的 localhost；题库仍仅在本机运行。

## 导出时附带已有答案

“导出时保留来源”和“导出时自动编号”旁新增“导出时附带已有答案（默认不带）”。默认不勾选，仍导出不带答案的试卷；勾选后，只把题库已经保存的答案附在对应题目下方，没有答案的题不添加答案栏，也不调用 AI 补答案。勾选题目导出和整套试卷导出均支持。

已有答案的图片、公式和表格沿用原导出方式保留；没有结构化格式记录的答案按保存的文字导出。若保存文字与原导入的答案记录不一致，以当前保存的答案为准，不恢复旧答案。导出接口使用布尔参数 `keep_answers`，缺省为 `false`。

## AI 新答案与自动接替补充（2026-10-07）

AI 改出的新题必须返回完整答案，并把答案及解析随变式保存。缺答案、无效响应或 GLM 请求失败时自动尝试 DeepSeek；明确遇到 GLM 额度耗尽时，暂停 GLM 10 分钟，让后续步骤继续用备用服务，之后重新尝试。新答案不回填或修改母题；无需重新导入旧题库。

带图题的初次、后续修改和重试均发送原图，审核仍独立进行。DeepSeek 输出上限默认 8192，可用 `DEEPSEEK_MAX_TOKENS` 调整（512 至 32768），格式兼容重试保留非推理模式和图片。已用两家的本机现有密钥分别实测六种题型，并验证带图自动接替、答案保存、查看及两种导出；记录、修复项和测试边界见 [AI 改题答案与双服务实测](docs/AI改题答案与双服务实测.md)。自动审核通过仍需教师复核。

## 试卷批量补答案与答案编辑（2026-10-07）

打开一套已保存的试卷，点击“AI批量补答案”，仅处理没有答案的题目，已有答案（包括图片答案）保留。原题不改写、不复制成新题。每题分别作答三次，再独立逐小问核对；两家服务均已配置时，第二次作答和核对优先使用 DeepSeek，其他步骤优先使用 GLM，失败时仍自动接替。

通过核对的小问自动保存为这道题的答案；存在实质分歧、计算问题、条件矛盾、图像不清或检查未完成的小问单独标为“存疑”，保留几次可能答案和依据，不以多数票决定。已保存的答案在题目下方可编辑并自动保存。存疑小问的修改先保存为草稿，老师点击“确认这一小问”后成为正式答案；其他已确认小问保留。答案与题库中的题目绑定，在其他试卷引用同一道题时也能看到。

勾选“导出时附带已有答案”后，导出已确认答案，并在存疑小问的位置标明“答案存疑，待教师确认”；可能答案不混入正式答案。默认导出仍不带答案。升级仅增加保存与任务结构，不会自动给整个题库补答案，也无需重新导入 Word。使用方法、真实接口测试及边界见 [试卷批量补答案与逐小问核对](docs/试卷批量补答案与逐小问核对.md)。

## 空答案标题的兼容修复

只有“【答案】”“答案：”等标题、空白段落或空表格的旧记录，按缺答案处理，能够进入 AI 批量补答案；页面显示“未填写”，导出不附上空答案标题。真正的文字答案、图片和公式仍保留。此修复直接兼容现有题库，不批量清洗或重写数据库，也不要求重新导入 Word；更新后重启程序并刷新页面，再发起补答案即可。

## 题库单题补答案与批量按钮防误触

全部题库页面不显示“AI批量补答案”，即使程序仍记着此前打开的试卷也不会显示；只有“正在查看某套试卷、只显示这套题目”的页面才提供批量补答案。双击已保存的试卷可进入此页面。

题库中缺答案的题目下方直接显示“AI生成答案”，不必先加入试卷或展开答案区域。一次点击只处理这一题，沿用三次独立作答、逐小问审核、自动保存和存疑候选保留。已有答案不重复生成，进行中的题目禁用按钮，重复请求只保留一个任务。后台不提供全题库批量补答案入口；没有指定试卷时只能提交一个真实、已收入题库的题号。

## 我的试卷：单击进入与颜色提示

现在单击“我的试卷”中的试卷名称即可进入这套试卷，替代此前的双击操作。再次点击当前试卷名称仍留在该试卷内，不会返回题库，也不会重置当前勾选状态。当前试卷名称按钮为鲜艳绿色，其他试卷名称保持灰色；进入试卷后，“退出当前试卷”按钮自动变为醒目的大红色。

点击“退出当前试卷”或“返回题库”会退出当前试卷，名称按钮和退出按钮恢复灰色，批量补答案入口隐藏。切换试卷时颜色立即跟随当前试卷；延迟返回的旧请求不会把页面切回先前的试卷。这些修改仅调整页面交互，已保存试卷及其题目不变。

## 全题库批量补答案：输入确认后启动

本次更新恢复全部题库页面的“对所有无答案的题目批量AI生成答案”按钮，替代上文旧版不提供全题库入口的说明。点击先弹出警告：资源消耗巨大、耗时可能非常长，可能产生大量费用；强烈推荐先把选定题目加入试卷，再从试卷批量生成答案。只有完整输入“我同意”，再点击“开始全题库任务”，才会创建任务。取消、关闭弹窗或输入其他文字都不会开始；每次打开弹窗都需重新输入，后台也校验确认文字。

此操作覆盖整个已收入题库，范围不受当前分页、勾选或筛选条件限制。已有答案、图片答案和待教师确认的候选结果会跳过；只有空答案标题的题仍算缺答案。生成仍使用三次独立作答、逐小问审核和自动保存；重复提交不为正在处理的题创建额外任务。页面显示整个任务的进度，可用“叫停所有当前AI生成”停止尚未完成的任务，已保存结果保留。已经发送的请求无法撤回，但叫停后其结果不会写入。

升级不会自动启动全题库任务，也不会重建题库或改变已保存试卷。重启程序并刷新页面即可使用。

# 开发日志和各种抱怨

先提前说一句，各位不管是谁，也别管是因为不想把数据挪到自己宿主机（真正用的电脑）上来污染环境、占用磁盘空间让它拉屎，还是单纯懒得折腾：求你了，真不要用 Grokbot 作为一个 coding agent，它实在是不行，真的不行！

它根本不管边界条件，而且完全不做测试。它不做测试就只能靠人肉去测、去发现问题，这东西非常耗元气。

不过好消息是，我找到了让 Codex 去使唤 Grokbot 的方法，非常之好。这样以后我就不用每次都在它们中间当中间人了。

---

我真没想到这事这么难，现在简直想死。

在初中九年级的学科里，化学和生物处理起来是旗鼓相当的难。题型太复杂了，对比英文题目，用 AI 生成是最简单的，因为基本全是纯文本；但化学题目全是多模态，各种形状各异的图。更麻烦的是模型未必支持多模态，此处点名 GLM-5.3：作为一个更聪明的大模型居然不支持输入图片，反而是 GLM-5.3 Flash 支持，真不知道怎么想的。

拿了一批最新的题目做测试，大概 170 多道题：

1. 最开始默认走 GLM，reasoning_level 设为 low，核验下来只有六七十道题答案没问题可以直接用。
2. 经过排错，发现其中有 50 多道题不是模型智力的问题，而是我这边作为 judge 的程序/language model 限制得太死。把限制放宽后，还剩下 70 多道存疑。
3. 接着把 reasoning_level 改成 high 重跑，但收效甚微，也就重新确认了十几道题。因为题目不只有单一答案的选择题，还有很多带多个小问的简答题；小问必须分开算，确定的小问算确定，存疑的还得留着，导致复杂度比看起来高得多。

折腾到这步，不管是调 harness 还是改 GLM 的 prompt 意义都不大了。我已经在想测测 Kimi 和 DeepSeek，看它们对九年级化学会不会有更好的表现。其实论智力水平，九年级化学真不需要多顶尖的模型，但当输入的题型本身形态极其复杂时，受现实条件制约，整件事就变得无比麻烦。

顺便说下目前答案判断（judge）的架构。同一道题的处理逻辑是：

1. 独立发出 3 次 request，由 3 个 solver 各自返回一份答案。
2. 答案比对与验证分两种情况：
(a) 语义判断：用另一个 language model 作为 judge，比对这 3 个输出。如果一致就通过；如果分歧很大（含语义判断），就标注为存疑。
(b) 硬匹配：针对答案形式明确的题目（如填"3mL"、"5.1g"的选择题或填空题），直接用 Python 写脚本做硬匹配。

但这套逻辑在题目类型（qtype）上踩了大坑。qtype 是题目导入时程序自动匹配的（判断是单选、多选、简答、计算还是实验题），但导入时经常出错。比如原本是一道选择题，导入时跟底下的内容粘连了，后面其实带了一堆小问，但程序仍把它当成一道简单的单选题。验证时 Python 脚本就按简单选择题去做硬编码比对，前面出的错直接引发后面的连锁反应，肯定过不了。

我总觉得在下游去修这些问题根本没有意义，拆东墙补西墙而已。真要解决，必须从最开始的题目切分源头去抓。

就先这样，真的要死了。
