# GLM 性能与图片问题排查

日期：2026-10-02。使用本机配置的 GLM API 密钥和既有模型：分析/初次生成/带图审核为 `glm-5.3-flash`，纯文字审核为 `glm-5.3`，端点为 `https://open.bigmodel.cn/api/paas/v4/chat/completions`。密钥未写入报告、题库或 Git。真实请求使用开发样本；正式题库只读核对。

## 已复现的主要原因

原程序强制开启推理，没有显式传 `reasoning_effort`，且所有 GLM 请求只有 4096 输出 token。官方文档说明 GLM-5.3 系列推理不能关闭，强度由 `low/high/max` 控制，默认 `max`。[官方 Chat Completion 参数说明](https://docs.z.ai/api-reference/llm/chat-completion)

带图分析实际返回 HTTP 200，`finish_reason=length`，`completion_tokens=4096`，其中 `reasoning_tokens=4067`，正文 `content` 为空。耗时 73.043 秒。接口收到图片并执行了推理，但预算耗尽，未产生应用所需的 JSON。原程序只将其归为“生成没有完成”，随后可能继续调用备用提供商，用户难以看到实际原因。

官方模型说明确认 GLM-5.3-Flash 支持图片，并允许通过 `image_url` 传 Base64 Data URL；本项目的发送形式在本次最小带图请求和完整流程中均实际成功。[GLM-5.3-Flash 官方说明](https://docs.z.ai/guides/vlm/glm-5.3-flash)

## 程序中的其他等待与图片问题

一次新变式会顺序请求“原题分析 → 改写 → 独立审核”；母题画像成功后可复用。审核结果为 SUSPECT/FAIL 时隐藏候选并自动重试，连续三次后停止。因此用户等待一题的时间可能是多个模型调用累加，不能与一轮聊天直接比较。后台原有并发上限为 10；本次未进行并发压测或修改并发策略，不声称已复现限流。

原来的 `_image_paths` 静默截取前 8 张图，并静默跳过不可读取的附件。正式库只读审计包含 3769 道图像题，235 道有超过 8 张不同图片；8321 个不同引用中有 4 个本地文件缺失，涉及 4 道题，引用扩展名为 WMF/TIF 的附件也无法通过原发送路径。这个统计不是“235 道错题”，需要核对是否题目粘连或正常多图；正式库未重新解析或修改。

原 HTTP 读取使用 `read(8192)`，可能等缓冲区填满才看到心跳，削弱 60 秒心跳限时判断；错误响应体被丢弃，超时和网络异常都变成不带原因的 503。新版改用 `read1`，按剩余时间设置响应 socket 超时，保留提供商错误代码并对密钥脱敏。

## 已实施的修复

- GLM-5.3 显式 high 推理强度，默认 8192 输出 token；环境变量支持调整，thinking 仍为 enabled。
- 识别 `finish_reason=length` 并解释输出额度耗尽，不把 HTTP 200 视为有效题目。
- 图片不再静默截断至 8 张；最多 32 张，超限、缺失或格式不可用明确报错，不把缺图请求退为纯文字。
- 界面区分等待、分析、改写和审核，显示具体失败原因；备用模型也失败时保留 GLM 根因。
- 42 项自动测试与已有 AI 离线状态测试通过。覆盖推理/额度参数、长度耗尽、错误脱敏、备用失败、多图完整发送、缺图和分块响应读取。

## 完整流程实测

完整流程在 `.dev/glm-investigation/data` 的独立数据库中运行，媒体读取开发样本，不启用正式题库工作线程；测试期间关闭备用提供商，以免把其他模型的结果计入 GLM。

纯文字题：分析 12.599 秒、改写 9.890 秒、独立审核 3.472 秒，总计 26.030 秒，审核 PASS。

带图实验题：分析 24.897 秒、改写 20.362 秒、独立审核 21.291 秒，总计 66.601 秒，审核 PASS；三步均实际发送原图，没有改为纯文字，也没有使用备用提供商。这证明这份样本已能完整返回，不代表所有化学图题都能自动正确改写。图片题完整流程仍约一分钟，主要是三轮实际推理累计，而非一轮 API 聊天。
